# Глава 27. Okkama среди языков

Предыдущие главы сравнивали Okkama с другими языками по одной конструкции:
числа в главе 5, типы в главе 4, коллекции в главе 8, роли в главе 14,
тесты в главе 15. Эта глава поворачивает сравнение. Она берёт шесть языков,
которые читатель этой книги, скорее всего, знает, — Java, Kotlin, Go, Rust,
Haskell и OCaml — и задаёт каждому те же вопросы, на которые манифест
ответил за Okkama (глава 3). Ещё три — Python, Swift и Erlang — идут
следом в разделах покороче, потому что к Okkama приходят и из них.

Сравнение языков легко сделать нечестным. Каждый из этих языков создан для
своей цели людьми, которые взвешивали те же компромиссы и выбрали иначе, и
за каждым десятилетия программ, которых у Okkama нет. Цель здесь — не
рейтинг. Она в том, чтобы показать, где выбор Okkama стоит среди решений,
принятых работающими языками, чтобы читатель, знающий один из них, увидел,
что знакомо, что иначе и чего недостаёт.

## 27.1 Правила рядом

| | Java | Kotlin | Go | Rust | Haskell | OCaml | Okkama |
|---|---|---|---|---|---|---|---|
| Отсутствие | `null` в любом ссылочном типе [@gosling2023] | nullable-типы `T?`, проверяемые [@kotlinspec] | `nil` у указателей, интерфейсов, словарей, срезов [@gospec] | `Option` [@klabnik2023] | `Maybe` [@haskell2010] | `option` [@ocamlmanual] | `Maybe` (глава 7) |
| Изменение | изменяемые поля; неизменяемые records | `val`/`var`; `copy` у data-классов [@kotlindata] | изменяемо | неизменяемые привязки, `mut` | неизменяемо; `IORef`, `ST` | неизменяемые привязки; изменяемые поля и `ref` | преемники; `Cell` в синхронном коде (глава 13) |
| Наследование реализации | классы, одиночное | классы, final, если не `open` [@kotlininheritance] | нет; встраивание | нет | нет | классы, редко используемые | нет (глава 2) |
| Контракты | интерфейсы с методами по умолчанию | интерфейсы | интерфейсы, структурные | трейты | классы типов | сигнатуры модулей | роли, номинальные, без тел (глава 14) |
| Отказы | проверяемые и непроверяемые исключения | непроверяемые исключения [@kotlinexceptions] | значения-ошибки, `panic` | `Result`, `panic` | `Maybe`, `Either`; исключения в `IO` | исключения, `result` | типизированные ошибки и паники (глава 10) |
| Освобождение ресурсов | `try`-with-resources | `use` [@kotlinuse] | `defer` | `Drop` | `bracket` [@hsexception] | `Fun.protect` [@ocamlfun] | `destroy`, `defer` (глава 11) |
| Целые | фиксированная ширина, заворачиваются | фиксированная ширина, заворачиваются | фиксированная ширина, заворачиваются | паника в отладочной сборке, заворот в выпускной | `Int` ограничен, `Integer` нет | фиксированная ширина, заворачиваются [@ocamlint] | неограниченные (глава 5) |
| Конкурентность | потоки; виртуальные потоки [@jep444]; структурная конкурентность в preview [@jep453] | корутины, структурные [@kotlincoroutines] | горутины и каналы | потоки; `async` с библиотечными средами | зелёные потоки, STM | домены [@ocamlparallel] и библиотеки | структурный async, процессы-исполнители (глава 20) |

Если читать строку, Okkama редко одинока. Rust, Haskell и OCaml разделяют
её ответ на отсутствие; Go, Rust и Haskell — её отказ от наследования
реализации; `Integer` в Haskell, к которому по умолчанию сводятся целые
литералы, неограничен, как `int` в Okkama. Если читать столбец, картина
меняется: ни один другой язык таблицы не даёт все ответы Okkama сразу, и
это единственная новая идея замысла (раздел 1.10).

## 27.2 Java

С Java Okkama спорит больше всего, потому что *Elegant Objects* —
дисциплина, которую Okkama превращает в правила, — написана для
программистов на Java (раздел 2.7). Почти каждое правило Okkama команда на
Java может принять соглашением: final-поля, никаких сеттеров, никакого
`null`, композиция вместо `extends`, маленькие интерфейсы с фейками. Чего
Java дать не может, так это гарантии. Соглашение держится, пока каждый
рецензент ловит каждое исключение из него; в Okkama это делает компилятор.

На часть тех же задач Java отвечает новыми возможностями. Records —
неизменяемые носители данных [@gosling2023], близкие к тому, что раздел 28.4
называет сокращением для объектов-данных. Виртуальные потоки делают
блокирующий код дешёвым [@jep444], а структурная конкурентность, в Java 21
ещё preview, даёт задачам родительскую область, которая их ждёт [@jep453].
Java сохраняет `null`, проверяемые исключения и наследование классов, и для
языка с такой базой установленного кода убрать их невозможно. У Okkama
такой базы не было — только поэтому она и смогла начать там, где кончается
лучшая практика Java.

## 27.3 Kotlin

Kotlin взял среду выполнения Java и поменял умолчания: классы final, пока
не объявлены `open` [@kotlininheritance], допустимость `null` — часть типа
и проверяется компилятором [@kotlinspec], data-классы приходят с `copy`
[@kotlindata], а все исключения непроверяемые [@kotlinexceptions]. Его
корутины структурны: корутина принадлежит области, которая не завершается,
пока не завершатся её дети [@kotlincoroutines], — это модель главы 20.

Отличие от Okkama — в степени. Kotlin делает безопасный выбор лёгким и
оставляет другой под рукой: `var`, `open`, `!!` и платформенные типы из Java
доступны, когда программисту они нужны. Okkama другой выбор убирает.
Команда на Kotlin может писать в стиле Okkama; программу на Okkama иначе не
напишешь.

## 27.4 Go

Go и Okkama согласны в большем, чем кажется по поверхности. Ни там, ни там
нет классов и наследования, оба считают ошибки значениями, которые функция
возвращает, а не бросает мимо вызывающего, оба освобождают ресурсы через
`defer` [@gospec], и оба держат язык маленьким. Расхождения столь же
коренные. Интерфейсы Go структурны, им удовлетворяет любой тип с нужными
методами; роли Okkama объявляются (раздел 14.2). Значения Go изменяемы, а
его `nil` достаёт до указателей, интерфейсов, словарей и срезов. И
инструкция `go` запускает горутину, которую никто не ждёт, —
неструктурная конкурентность, против которой выступает глава 20.

Go выбрал простоту языка и оставил дисциплину программисту и инструментам
вроде линтеров. Okkama выбрала простоту *программы*: меньший набор того,
что может пойти не так, купленный более строгим языком.

## 27.5 Rust

Rust — ближайший родственник по цели. В нём нет `null`, нет наследования,
значения неизменяемы, пока не объявлены `mut`, ошибки — `Result`, а ресурсы
освобождаются через `Drop`, когда их владелец выходит из области
[@klabnik2023]. Его трейты — номинальные контракты, как роли, хотя могут
нести методы по умолчанию. Rust отличается тем, чего он требует от
программиста, чтобы туда прийти. Владение и заимствование проверяются при
компиляции и записываются в программе: времена жизни, `&` и `&mut`,
перемещения. Награда — безопасность памяти без сборщика мусора и контроль
над каждым выделением.

Okkama заключает другую сделку. Её памятью управляют автоматически, а
детерминированное уничтожение оставлено ресурсам (раздел 11.1), так что
большинство программ о владении не говорит вовсе, а ресурс освобождается
областью, которая его создала, без аннотаций. В Rust целые ещё и
переполняются: арифметика паникует в отладочной сборке и заворачивается в
выпускной [@klabnik2023], тогда как целые Okkama растут (глава 5).
Программу, которой нужен контроль Rust над памятью, следует писать на Rust.

## 27.6 Haskell

Haskell — самый чистый язык таблицы: значения никогда не меняются, эффекты
заключены в типы вроде `IO`, отсутствие — `Maybe`, контракты — классы типов
[@haskell2010]. Многое в словаре Okkama пришло из этой линии через ML:
перечисления с полезной нагрузкой и `match` (глава 16), `Maybe`, роли,
похожие на классы типов с объявленными экземплярами (раздел 14.9).

Важны два отличия. Haskell выводит типы по всей программе, а Okkama —
только внутри тел и требует аннотировать каждое объявление (раздел 4.5). И
Haskell по умолчанию ленив: выражение вычисляется, когда нужно его
значение, что делает одни программы изящными, а стоимость и порядок
вычислений — менее заметными. Okkama энергична, и её порядок вычислений
фиксирован и записан (раздел 9.7). Чистота Haskell обеспечивается типами;
неизменяемость Okkama — отсутствием присваивания, а её эффекты — обычные
вызовы объектов, несущих полномочия на них (глава 21).

## 27.7 OCaml

OCaml — это ML с объектами и промышленным опытом. Привязки неизменяемы,
отсутствие — `option`, отказы — исключения или `result`, а модули с
сигнатурами и функторами — его главный инструмент абстракции
[@ocamlmanual]. В нём есть и система классов с наследованием, которой
большая часть кода на OCaml не пользуется, и изменяемые поля записей и
ссылки, когда они нужны программе. Его целые фиксированной ширины и
заворачиваются при переполнении [@ocamlint]. С OCaml 5 домены выполняются
параллельно на нескольких ядрах [@ocamlparallel].

OCaml показывает, что язык, ориентированный на выражения, неизменяемый по
умолчанию и с алгебраическими типами данных, может быть быстрым и
практичным. Он сохраняет запасные выходы — изменяемые поля и классы, —
которые Okkama убрала, и у него есть рекурсивные варианты и вложенные
образцы, которых у Okkama пока нет (раздел 28.2).

## 27.8 Python

На Python читатель, скорее всего, хоть что-то писал, и его декларация
замысла среди прочего говорит, что практичность важнее чистоты
[@peters2004]. Некоторые ответы Okkama — и ответы Python. Его `int` с PEP 237
стал единым неограниченным типом [@pep237], точные дроби — стандартный модуль
(`fractions.Fraction`) [@pyfractions] там, где у Okkama встроенный `rat`, а
`with` освобождает ресурс, когда блок заканчивается [@pep343], — та же мысль,
что за `defer` и `destroy`. С Python 3.11 `asyncio.TaskGroup` дожидается
всех созданных в нём задач, когда его блок завершается [@pyasyncio], — это
структурное ожидание главы 20 в виде библиотечного объекта.

Различия в том, где живут правила. Типы — необязательные аннотации
[@pep484], которые проверяют инструменты вне интерпретатора; программа с
неверными аннотациями всё равно выполняется. `None` может стоять там, где
ждут любое значение, объекты изменяемы, если класс не позаботился об
обратном, а класс может наследовать от нескольких других. Вызов работает на
любом объекте с нужными методами — структурная типизация, которой раздел
14.2 противопоставляет роли. Исключения не проверяются, и голый
`except Exception` ловит и ошибки, и баги, тогда как Okkama разделяет эти
два канала (глава 10). `float` хранит бесконечности и NaN (раздел 5.5).

Python меняет гарантии на скорость, с которой пишется первая версия, и делает
это сознательно. Программа на Python, которая следует правилам Okkama по
соглашению — замороженные dataclass, никакого `None` в сигнатурах,
аннотации, проверяемые в непрерывной интеграции, — по форме близка к
программе на Okkama. Ей недостаёт гарантии, что модуль, написанный кем-то
другим, следует тем же соглашениям.

## 27.9 Swift

Swift, представленный Apple в 2014 году, — промышленный язык, ближе всех к
Okkama по умолчаниям [@swiftbook]. Значения типов `struct` и `enum`
копируются, а не разделяются; `let` объявляет константу; отсутствие —
опционал `T?`, который проверяет компилятор; перечисления несут связанные
значения и разбираются через `switch` с проверкой полноты. Целочисленная
арифметика по умолчанию останавливается при переполнении, а для
заворачивания нужны явные операторы вроде `&+`. Структурная конкурентность
— `async let` и группы задач — часть языка [@se0304].

Swift, как и Kotlin, держит оба мира. Рядом с типами-значениями у него есть
классы с одиночным наследованием и разделяемыми изменяемыми экземплярами. Его
протоколы — номинальные контракты, как роли, но расширение протокола может
дать им реализации по умолчанию, то наследование поведения, от которого
Okkama отказалась (раздел 1.9, #146). Память управляется подсчётом ссылок,
поэтому `deinit` экземпляра класса выполняется, как только уходит последняя
сильная ссылка: память и ресурсы освобождает один механизм, тогда как Okkama
собирает память, а детерминированное освобождение даёт только объектам с
`destroy` (глава 11). Функция, которая может отказать, помечается `throws`,
а каждый вызов — `try`; сигнатура Okkama не говорит, что действие может
отказать (раздел 10.19).

## 27.10 Erlang

Erlang создавали в Ericsson для телефонных коммутаторов, которые не должны
останавливаться [@armstrong2003]. Его данные неизменяемы, переменная
связывается один раз, целые не ограничены, а функции разбирают аргументы
сопоставлением с образцом. Единица конкурентности в нём — процесс:
изолированный дешёвый поток со своей кучей, который ничего не разделяет и
общается только сообщениями [@erlangref]. Единица обработки отказов — тоже
процесс. Вместо того чтобы обрабатывать каждую ошибку там, где она
случилась, процессу, который её встретил, позволено упасть, а связанный с
ним супервизор перезапускает его в известном состоянии.

Okkama разделяет первую половину этого замысла: неизменяемые значения,
никакого разделяемого изменяемого состояния между задачами и образец
владельца состояния из раздела 20.6, где одна задача владеет куском
состояния, а остальные шлют ей запросы по каналу, — так состояние держит
процесс Erlang. Отличается вторая половина. Задачи Okkama работают в одной
программе и структурированы: отказ доходит до задачи, которая ждёт, как
типизированное значение, которое она может обработать, и ничто не
перезапускается само. Изоляцию по памяти дают рабочие процессы (глава 21) —
ценой отдельной программы. Кроме того, Erlang типизирован динамически, а
статическая проверка оставлена необязательным инструментам.

## 27.11 Перенос, шаг за шагом

Правила проще всего сравнить на одном маленьком классе. Вот банковский счёт
на Java, написанный так, как его написал бы учебный курс:

```java
import java.util.HashMap;
import java.util.Map;

public class Account {
    private final String owner;
    private long cents;

    public Account(String owner, long cents) {
        if (cents < 0) throw new IllegalArgumentException("negative balance");
        this.owner = owner;
        this.cents = cents;
    }

    public void withdraw(long amount) {
        if (amount > cents) throw new IllegalStateException("overdrawn: " + cents + " < " + amount);
        cents -= amount;
    }

    public String shown() { return owner + " " + cents; }

    public static void main(String[] args) {
        Map<String, Account> accounts = new HashMap<>();
        accounts.put("ada", new Account("ada", 1000));
        Account ada = accounts.get("ada");
        ada.withdraw(300);
        System.out.println(ada.shown());
        Account bob = accounts.get("bob");
        System.out.println(bob == null ? "no bob" : bob.shown());
        try {
            ada.withdraw(5000);
        } catch (IllegalStateException e) {
            System.out.println("refused: " + e.getMessage());
        }
        System.out.println("in the map: " + accounts.get("ada").shown());
    }
}
```

Запущенный на Java 26, он печатает:

```text
ada 700
no bob
refused: overdrawn: 700 < 5000
in the map: ada 700
```

Каждое изменение при переносе — решение, которое версия на Java оставила
неявным.

- **Баланс больше не изменяемое поле.** `withdraw` становится `withdrawn`,
  преемником (глава 13). Словарь в Java показывает изменённый баланс,
  `ada 700`, потому что словарь и `ada` делят один изменяемый объект.
  Словарь Okkama по-прежнему держит счёт, который ему дали, `ada 1000`, а
  новое состояние попадает в словарь, только когда программа его туда
  кладёт: `accounts + ["ada": ada]`. При переносе на каждой мутации
  приходится решать, кто должен увидеть изменение.
- **Отсутствующий ключ — больше не `null`.** `accounts.get("bob")` возвращает
  `null`, и код должен не забыть это проверить. В Okkama отсутствующий ключ
  — отказ, если поиск не говорит, что делать: здесь `accounts.has`, или
  `accounts["bob"] else …`, или `Maybe` (глава 7).
- **Исключения становятся словарём.** `IllegalArgumentException` и
  `IllegalStateException` говорят, что что-то не так; перечисление `Refused`
  говорит, что именно: `negative` и `overdrawn(balance, wanted)`. Вызывающий
  ловит случай, который обрабатывает, и читает его нагрузку, а не разбирает
  сообщение (глава 10).
- **Конструктор сохраняет проверку.** `if … throw` из Java становится
  `confirm … else throw`, и ни в одном из языков счёт не может существовать
  с отрицательным балансом.

Чего перенос не потребовал: геттеров (`shown()` — единственный вопрос,
который задаёт программа), ключевого слова `final` (все поля и так
неизменяемы) и проверки, что `owner` не null (`string` не может
отсутствовать). Перенос примерно той же длины, что и оригинал; он больше
говорит о том, что может произойти.

## 27.12 Что показывает сравнение

Выделяются три вещи.

- **Правила Okkama не новы.** Каждое пришло из языка этой таблицы или из
  литературы за ним. Новое — то, что все они выполняются одновременно, в
  одном языке, по правилу, а не по соглашению.
- **Другие языки сохраняют выходы.** `var` в Kotlin, `unsafe` в Rust
  [@klabnik2023], изменяемые поля OCaml, `null` в Java: каждый язык с более
  безопасным умолчанием сохраняет и менее безопасный выбор для программ,
  которым он нужен. У Okkama выходов меньше: `Cell` для синхронного кода,
  `Atomic` для состояния, общего для задач, и natives для хоста.
  Программа, которой нужен другой выход, — программа, которую Okkama
  обслуживает плохо, и глава 28 перечисляет, где это видно.
- **Самое большое различие — зрелость.** У каждого языка таблицы есть
  библиотеки, инструменты, книги и рабочие системы, построенные за годы и
  десятилетия. У Okkama есть набор тестов соответствия, стандартная
  библиотека, которую переписывают, и эта книга. Сравнение замыслов — лишь
  половина сравнения языков.
