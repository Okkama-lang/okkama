# Chapter 21 — archived implementation passages

Replaced mixed paragraphs are preserved in full for context.

## 21.1 Одна дверь к хосту

described 0.5.x

У нативного объявления есть сигнатура и нет тела. Это запрос: когда
программа вызывает `monotonic_clock()`, движок ищет провайдера,
зарегистрированного под этим модулем и именем, и запускает его. На IR-движке
и на Sparrow провайдер написан на Rust, на JVM — на Java, и все три
проверяются на одинаковые результаты (глава 26). Модули `runtime/*` —
единственное место стандартной библиотеки, где объявлены нативы; всё выше —
обычный Okkama, который можно читать, тестировать и подменять фейками.

## 21.3 Нативные объекты: handle

described 0.5.x

Все три движка печатают одни и те же четыре строки. Программы редко держат
handle напрямую: std заворачивает каждый в объект с `destroy` (глава 11), так
что `FileRoot`, `TcpConnection` и соединения с базами закрывают свои handle,
когда кончается область их владельца, а сам handle — поле, до которого никто
другой не дотянется.

## 21.5 Запуск других программ

described 0.5.x

Раздел 20.4 показал другой способ, которым программа на Okkama запускает
процесс: `spawn` *синхронного* действия исполняет это действие в
процессе-воркере, параллельно с программой. С точки зрения этой главы воркер
— команда, которую рантайм собирает сам, и каждое его свойство следует из
этого.

**Воркер — та же программа.** Рантайм запускает программу ещё раз, тем же
движком, в режиме, который вместо `main` исполняет одно действие: Tomato —
её `.spb` (программа, скомпилированная в памяти, сначала пишется во
временный файл), IR — её исходные файлы, JVM — её классы. Потомок получает
окружение и рабочую директорию родителя такими, какими их видит рантайм
родителя, так что относительный путь значит в воркере то же, что в родителе.
Он не получает ни кучи родителя, ни его открытых handles, ни его задач. Нет ни
fork, ни копии памяти: воркер стартует пустым, загружает тот же код и
получает receiver и аргументы.

## 21.5 Запуск других программ

described 0.5.x

**Отмена — это kill.** Отмена из раздела 20.5 кооперативна: она доходит до
задачи в точке приостановки и разворачивает её, вместе с defer и `destroy`. У
воркера — синхронного действия без точек приостановки — сотрудничать не с
чем. Отмена его Future убивает процесс (SIGKILL): на Tomato и IR воркер
возглавляет свою группу процессов, и уходит вся группа, вместе с процессами,
которые воркер запустил. Future завершается `Cancelled` только после того,
как потомок собран, так что код после `await` никогда не работает рядом с
воркером, который ещё пишет. Воркер, отменённый до запуска своего процесса,
не запускается. Его defer не выполняются, и воркер, которому нужно прибрать
за собой, не надо отменять: лучше передать ему срок среди аргументов. (До
0.5.3 IR и JVM посылали TERM и сразу завершали Future; тикет #359.)

## 21.5 Запуск других программ

described 0.5.x

Стандартный вывод буферизуется (тикет #132). Терминал получает каждую строку,
как только она кончилась; канал или файл — блоками по 64 КиБ;
`Stdout().flush()` выписывает накопленное. Порядок, который видит читатель,
сохраняется: рантаймы сбрасывают буфер перед записью в стандартный поток
ошибок, перед чтением стандартного ввода с терминала, перед запуском
дочернего процесса, перед записью в терминал и при завершении программы.
Причина — простая арифметика: 200 000 строк в канал занимали у Sparrow 155 мс,
у IR-движка 1 084 мс, пока каждая строка была отдельным системным вызовом, и
56 мс и 590 мс после. JVM по-прежнему сбрасывает каждую запись.

## 21.5 Запуск других программ

described 0.5.x

Строка теряет LF и один CR перед ним, так что файл, записанный в Windows,
читается так же, как записанный в Unix. Ввод, который не является корректным
UTF-8, по умолчанию — отказ; `Stdin(decoding: InputDecoding.lenient)` вместо
этого ставит U+FFFD на место каждой плохой последовательности, как браузеры,
а `Stdin().chunks(size: 65536)` идёт по байтам. Все `Stdin()` читают через
один буфер рантайма, поэтому программа может прочесть заголовок по строкам, а
остальное байтами и не потерять то, что лежало между ними.

## 21.6 Что может запретить встраивающее приложение

described 0.5.x

Те же `Limits` несут бюджеты модели безопасности: шаги, память, вывод и флаг
прерывания, который хост может поднять из любого потока. Исчерпание
останавливает запуск собственным отчётом, который не перехватывает никакой
`catch` (глава 10). С 0.5.1 бюджет памяти может мерить один runtime, а не
весь процесс (`MemoryScope::Runtime`, issue #269): на Sparrow он читает
собственную кучу runtime, так что хост может запускать несколько программ
рядом, и та, что выросла за свой бюджет, останавливается, а остальные
продолжают.

### 21.6.1 Встраивающее приложение целиком

Хост, который запускает чужой плагин, излагает весь договор одним значением.
На Rust, поверх `sparrow-core`:

```rust
use std::sync::Arc;
use std::sync::atomic::{AtomicBool, Ordering};
use sparrow_core::budget::{Limits, MemoryScope, NativeGroup};

fn run_plugin(spb: Vec<u8>, arguments: Vec<Vec<u8>>, stop: Arc<AtomicBool>)
    -> Result<i64, sparrow_core::Error>
{
    let limits = Limits {
        steps: Some(200_000_000),          // входы в функции и обратные рёбра циклов
        memory: Some(64 << 20),            // 64 МиБ собственной кучи этого рантайма
        memory_scope: MemoryScope::Runtime,
        output: Some(1 << 20),             // 1 МиБ stdout и stderr
        interrupt: Some(stop),             // поднять может любой поток
        natives: Some(vec![NativeGroup::Clock]),
    };
    // Команды воркера нет: `spawn` синхронного действия здесь завершится ошибкой.
    sparrow_core::run_limited(spb, arguments, false, Vec::new(), limits)
}
```

Каждое поле — одна строка политики хоста, и ни у одного поля нет значения по
умолчанию, которое что-то разрешает. `natives: Some(vec![NativeGroup::Clock])`
— ответ на вопрос «что эта программа может делать за своими пределами?»:
читать часы, а также считать и печатать, как может любая программа. Плагин,
который откроет файл, упадёт на этом вызове с отчётом, называющим
недостающую группу. Плагин, который зациклится, исчерпает шаги; тот, что
строит неограниченный список, исчерпает свои 64 МиБ; тот, что печатает в
цикле, исчерпает вывод. Сторожевой поток хоста может закончить любой из них
раньше: `stop.store(true, Ordering::Relaxed)`. Каждый такой конец — своё
сообщение (`Execution budget exhausted: steps`, `… memory`, `… output`,
`Execution interrupted`), его не перехватит ни один `catch` плагина, и после
него не выполняется ни один `destroy`: рантайм выбрасывается вместе с кучей.

`MemoryScope::Runtime` — причина, по которой один процесс хоста может
запускать много таких плагинов сразу. Область по умолчанию, `Process`, читает
распределитель памяти процесса через пробу, которую ставит встраивающее
приложение. Это верно для CLI (один запуск на процесс) и неверно для сервера,
где память одного плагина была бы записана на счёт всех. С `Runtime` Sparrow
читает байты своей кучи — её страницы и большие объекты и Rust-память,
которой владеют её объекты, — так что у каждого рантайма свой бюджет и проба
не нужна.

Пустая команда воркера — тоже решение. Процессы-воркеры (21.5.1) запускают ту
же программу заново дочерним процессом, так что хост, который их разрешает,
даёт плагину способ создавать процессы. Ядро отказывает в `spawn`
синхронного действия, если хост не дал ему команды, а хост, который её даёт,
должен разрешить и `NativeGroup::Process`, который об этом и говорит.

Гарантии держатся ровно настолько, насколько держится классификация
нативов. Каждый натив `runtime/*` должен быть назван либо в группе, либо
среди чистых. Натив, которого нет ни там, ни там, запрещён всякий раз, когда
хост ограничивает группы, а тест останавливает сборку, если модуль остался
неназванным. До 0.5.3 таблица открывалась по умолчанию: модуль, которого
она не называла, считался чистым, и два натива, читающих факты о хосте, —
предпочитаемые языки и доверенные сертификаты системы, — проходили мимо
хоста, запретившего `Env` (тикет #361). То, чего группа выразить не
может, например «файлы, но только в этом каталоге», выражается средствами
самой программы: хост передаёт `FileRoot` аргументом (21.4), и программа
ничего за его пределами назвать не может.

## 21.9 Чего стоит такой замысел

described 0.5.x

Узкий ABI нативов стоит копий: строка или массив байт идут через границу по
значению, и большой копируется при каждом переходе. Непрозрачные handle
стоят поиска в таблице и проверки поколения на каждом вызове. Явные
полномочия стоят параметров: функция, читающая один файл, принимает объект,
который называет, где ей можно читать, там, где другой язык дал бы ей открыть
путь. Полные полномочия командной строки стоят изоляции, которую хосту
приходится обеспечивать самому.

Покупает замысел короткий ответ на вопрос «что может эта программа»: нативы,
до которых дотягиваются её импорты, отфильтрованные группами, которые
разрешил её хост. Этот ответ помещается на одной странице, и все движки дают
один и тот же.


## Глава 21. Процессы, нативы и полномочия

described 0.5.x

Всё, что строили предыдущие главы, вычисляет. Объект держит значения,
действие выводит из них новые, future ждёт результата, который даст другая
часть программы. Ничто из этого не выходит за пределы программы. Внешний
мир — файлы, сокеты, часы, другие процессы, терминал — достижим только одним
путём: через *натив*, функцию, которую предоставляет движок, а программа
объявляет. Эта глава — о границе: как натив объявляют и кто на него отвечает,
что держит программа, когда держит файл или сокет, как полномочия над хостом
передаются обычным значением, как работа уходит в другой процесс и что может
запретить встраивающее приложение.

## 21.1 Одна дверь к хосту

described 0.5.x

Программа компилируется и запускается. `before the call` печатается; вызов
падает с `RuntimeError: Native symbol "bible/unregistered@1::vault_open/1"
is not registered`, и запуск завершается со статусом 1. Имя натива — это его
модуль, мажорная версия модуля, собственное имя и арность, и отвечает на него
только провайдер, зарегистрированный ровно под этим именем. Программа не может
добраться до хоста, придумав объявление: набор дверей — тот, с которым собран
движок, плюс то, что добавит встраивающее приложение (раздел 21.6).

## 21.2 Что натив может принять и вернуть

described 0.5.x

Вызов возвращает future, как любое асинхронное действие. Движок запускает
операцию хоста, не блокируя планировщик, остальные задачи тем временем
работают, и future завершается, когда хост сообщает результат (глава 20).
Программа никогда не видит потоков и обратных вызовов хоста.

## 21.3 Нативные объекты: handle

described 0.5.x

- `close` оба раза возвращает `true`. Закрытие идемпотентно, и ресурс за
  handle освобождается ровно один раз.
- Запись через закрытый handle не попадает в переиспользованный дескриптор и
  не роняет программу: она завершается `NativeFailure` с кодом
  `already_closed`, который берёт обычный `catch`.
- Если бы программа забыла `close`, runtime закрыл бы все оставшиеся handle
  при завершении запуска, как бы тот ни завершился, не дожидаясь сборщика
  мусора.

## 21.7 Командная строка сохраняет полномочия пользователя

described 0.5.x

Другие системы ставят границу в другом месте. Deno запускает скрипт вообще
без доступа и требует флагов вроде `--allow-read=./data` и
`--allow-net=example.org` [@deno]. Системный интерфейс WebAssembly даёт
модулю только те каталоги, которые хост заранее открыл для него, в виде
дескрипторов, — так, как работает `FileRoot` [@wasi]. Java пошла обратным
путём: её Security Manager, проверявший разрешения на каждом чувствительном
вызове внутри одного процесса, объявлен к удалению в Java 17, потому что им
мало кто пользовался, а каждую библиотеку приходилось писать под него
[@jep411]. Выбор Okkama — между ними. Внутри языка std передаёт полномочия
значениями (раздел 21.4), а хост, встроивший runtime, может отрезать целые
группы. Ниже этого изолирует операционная система: контейнер, jail,
пользователь без прав. Граница проведена там, потому что песочница на уровне
интерпретатора не прочнее своего самого небрежного натива, а модули runtime
объявляют их 653.
